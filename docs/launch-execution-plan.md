## 2. 首发目标与数量口径

> 本节更新时间：2026-07-27 17:11（Asia/Shanghai）

首发采用 PRD 每类最低数量，先完成质量闭环：

| 类型  | 真实主题数 | 本地化文件数 | 发布条件                         |
| ----- | ---------- | ------------ | -------------------------------- |
| Build | 2          | 4            | 两个主题均有中英文核验版本       |
| Boss  | 2          | 4            | 不使用虚构首领或未经验证机制     |
| Item  | 2          | 4            | 物品属性、用途和版本均可追溯     |
| Skill | 2          | 4            | 技能机制和辅助选择逐项核验       |
| Guide | 2          | 4            | 步骤完整且能独立解决真实问题     |
| Patch | 1          | 2            | 仅原创概括并链接官方补丁说明     |
| 合计  | 11 个主题  | 22 个文件    | 每个语言版本独立审核，不批量放行 |

这里的“11 个主题”是内容选题口径，“22 个文件”是中英文独立页面口径，不能把翻译版本
误算成额外选题，也不能因为已有 12 个草稿模板就认为真实内容已经完成。

现有模板保留草稿状态。真实文章应复制对应结构后改用真实 `contentId`、Slug 和标题，不直接
发布 `*-template` 文件。

## 3. 设计方案

### 3.1 架构保持不变

```text
官方来源 / 游戏内核验
        ↓
仓库 Markdown/MDX 草稿
        ↓
Schema、关系、来源与发布门禁
        ↓
人工事实审核 + 中英文语言审核
        ↓
React Router 构建期静态预渲染
        ↓
build/client/
        ↓
静态 CDN、Sitemap、搜索索引
```

不引入数据库或 CMS。`content/` 继续作为内容唯一来源，`status` 与 `draft` 继续作为唯一
生产边界，所有公共正文继续在构建时写入完整 HTML。

### 3.2 内容状态设计

当前 Schema 只保留必要的两种发布状态：

1. `status: draft`、`draft: true`：研究、写作、翻译、审核中的内容。
2. `status: published`、`draft: false`：全部核验完成并允许生产消费者读取。

`patchStatus` 表示版本适用性，不代替发布状态：

- `current`：已在当前目标 Patch 核验。
- `supported`：不是最新主题，但仍确认可用。
- `under-review`：新 Patch 后等待复核，不能冒充已确认最新。
- `legacy`：保留历史价值并明确过时范围。

不增加模糊的“半发布”状态。审核进度记录在上线任务台账中，只有最终切换才修改生产状态。

### 3.3 研究与来源设计

每个主题先建立事实清单，再开始成文：

| 事实类别         | 优先来源                                     | 允许的辅助来源           |
| ---------------- | -------------------------------------------- | ------------------------ |
| Patch 改动       | 官方补丁说明                                 | 社区讨论只用于发现影响点 |
| 技能、物品、首领 | 官方资料或可复现的游戏内核验                 | 社区资料用于交叉检查     |
| Build 结论       | 游戏内测试、明确的 Patch 条件与可解释方法    | 外部规划工具             |
| 操作与流程       | 可复现游戏内步骤                             | 社区问题用于发现痛点     |
| 搜索需求         | 搜索结果意图、站长工具数据或社区高频真实问题 | 不复制第三方文章结构     |

来源必须支持具体事实，不允许用一个泛化主页链接为整篇文章背书。社区内容不得整段改写，
截图、图片和数据库文本必须确认授权或改为原创表达。

### 3.4 双语设计

- 同一主题的中英文文件共享 `contentId` 和稳定 Slug。
- 先完成事实层审核，再分别进行英文和中文表达审核。
- 中文保留社区通用的 Build、Boss 等术语，并在首次出现时给出清晰解释。
- 不使用未经人工审校的机器直译直接发布。
- 两种语言可以在同一发布批次上线；若一方未完成，另一方不得生成指向不存在译文的
  `hreflang`。

### 3.5 内容集群与内链

首发不是 11 篇孤立文章，而是围绕少量真实问题形成集群：

```text
Patch 摘要
  ├─ 影响 Build A / Build B
  ├─ 影响 Skill A / Skill B
  └─ 触发需要复核的 Guide

Build
  ├─ 使用 Skill
  ├─ 关联 Item
  ├─ 指向升级 Guide
  └─ 指向相关 Boss 应对
```

关联内容必须在同语言中已发布。建议按完整集群一次切换状态，避免某篇已发布文章引用仍为
草稿的目标而触发构建失败。

### 3.6 视觉设计

- 延续当前暗色原创设计系统，不使用官方 Logo 或未授权游戏素材。
- 每个主题优先使用信息型原创图：流程图、阶段图、属性优先级图或抽象场景插画。
- 卡片与详情图使用 WebP/AVIF，提供固定宽高、响应式尺寸和准确替代文本。
- 同一原创视觉可在中英文版本共享，但图中含文字时必须分别本地化。
- 图片来源、作者和授权状态应在发布审核中留痕。

### 3.7 发布与监控设计

- Preview 一律 `noindex`，不提交给搜索引擎。
- 生产只部署 `build/client/`，未知路径返回真实 404。
- 首发先配置 Google Search Console；Bing Webmaster Tools 可选。
- 初始不启用 Analytics、Ads 或第三方跟踪，避免在缺少同意机制时扩大隐私范围。
- 每次官方 Patch 发布后，将可能受影响内容切换或评估为 `under-review`，再逐篇复核。

## 9. 推荐执行顺序

LAUNCH-001～011 已完成，现执行 `LAUNCH-012`。生产部署与自定义域名已获授权并完成；`pages.dev` 重定向和 Search Console Sitemap 提交仍需在对应步骤单独确认。

完成 `LAUNCH-001` 后，严格按编号推进。内容任务可以在人员充足时并行研究，但每个文件
仍必须独立核验，发布状态必须在完整内容集群和质量门禁通过后统一切换。

## 10. 每次任务的统一完成定义

每个 `LAUNCH-*` 任务结束前必须：

1. 更新本文件对应任务状态或单独的上线执行台账。
2. 更新 `docs/project-progress.md` 的任务外事项与会话时间线。
3. 修改位置记录绝对更新时间。
4. 运行 `npm run validate:content` 和与该任务相关的测试。
5. 涉及生产消费者时运行完整 `npm run quality`。
6. 直接检查构建产物中没有草稿、占位符、测试夹具或本地 URL。
7. 未通过事实审核的文章保持 `draft`，不得为了完成任务绕过发布门禁。
